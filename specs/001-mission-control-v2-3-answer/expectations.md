- E1: Started without `--remote-port`, the server opens only the `:4319` sockets. On `:4319`, POST `/api/remote/pair` and `/api/remote/answer` and GET `/api/remote/prompts` and `/api/remote/events` all return 404. A wrong Host or Origin still gets 403 and a non-JSON POST still gets 415.
- E2: With `--remote-port`, the second listener binds only 127.0.0.1. A request with a Host other than the configured `*.ts.net` name, a POST whose Origin is not `https://<that name>`, or a POST with no Origin is refused with 403. A non-JSON POST is refused with 415. Dashboard APIs (items, calls, usage) return 404 there.
- E3: A pairing link from `mission-control remote pair` pairs a phone once and sets a `__Host-` cookie that is HttpOnly, Secure, SameSite=Strict and Path=/. Using the same link again, after 10 minutes, or with an unknown token is refused. `remote/pairing.json` holds only a hash, never the token.
- E4: The dashboard's Remote page and `remote devices` list the paired device. After `remote revoke <id>`, the device leaves both lists, and the phone's next request is refused with a "revoked, pair again" screen.
- E5: A paired phone lists the same open prompts as the desktop Needs you queue, each with the same tool, masked target and "asked … ago". The list updates without a reload when a prompt opens or closes.
- E6: Tapping Allow or Deny on a Claude Code or Codex permission prompt makes the session continue or be denied. The card then clears on both the phone and the desktop.
- E7: Tapping an option on a Claude Code AskUserQuestion prompt continues the session with that option as the answer. Multi-select and free-text questions show as "answer where the agent runs", with no buttons. Permission cards never offer "always allow".
- E8: A prompt that was replaced between display and tap is refused with "prompt changed", and the new prompt stays open and unapproved. A prompt answered from another device shows "already answered". One answered in the terminal shows "answered in terminal". One that timed out shows "no longer waiting".
- E9: When the server is down, no device is paired, or nobody answers within the wait (default 120 s, set by `remote.waitSeconds`), the hook prints nothing and exits 0, and the terminal prompt handles the request.
- E10: A subagent's permission request and every non-answerable hook event return immediately, as before v2.3, with no wait.
- E11: `hooks install` prints timeouts of `waitSeconds + 15` on Claude PermissionRequest and PreToolUse, and on Codex PermissionRequest (other Codex entries stay at 10). The output contains no `onFailure`.
- E12: Each accepted phone decision adds exactly one line to `~/.mission-control/audit.jsonl`, which has mode 0600. The line has the device, prompt id, decision, tool, target hash and timestamp, and no raw command, path, question, option text or secret. Refused taps add no line.
- E13: The phone app passes an installability check over HTTPS and can be installed. Offline it opens its shell, shows "offline, can't answer", and has every answer button disabled. No `/api/` response is ever stored in its cache.
- E14: `docs/remote-answering.md` states which spike outcome (A, B or C) was observed, with the Claude Code and Codex versions. The README Security section describes the second listener, pairing, the audit log, the hook wait, the Tailscale setup, the Funnel warning, and that Codex hooks are "a guardrail, not a complete enforcement boundary".
